# 旅遊行李清單管理系統(Travel Packing List) — Requirements

本文件依初步規劃整理需求，保留 FR-01～FR-04 與 BR-01～BR-11 編號，新增 FR-05～FR-07 與 BR-12～BR-14 支援個人清單調整。本階段為 **Design Only（尚未實作）**，不產生程式碼、資料庫或自動化測試。

## 1. Problem 與 Target User

一般旅客在準備行李時，需依旅遊天數、氣候條件、活動類型及國內／國外情境，自行決定攜帶物品及數量。每次重新建立清單耗費時間，也可能遺漏重要用品。

目標使用者為需要自行規劃與整理旅遊行李的一般旅客。系統以固定規則產生具推薦原因的清單，並追蹤準備狀態，減少重複規劃與遺漏。

## 2. Scenario 與核心亮點

旅客準備進行 5 天國內登山旅行，建立計畫時輸入 `days = 5`、`climate = COLD`、`activity = HIKING`、`region = DOMESTIC`。

系統依四項條件推薦以下清單，所有項目初始皆為未準備（`is_packed = false`）：

| 物品 | 建議數量 | 單位 | 推薦原因 | 規則 |
| --- | ---: | --- | --- | --- |
| 上衣 | 5 | 件 | 根據旅遊天數 | BR-04 |
| 褲子 | 3 | 件 | 根據旅遊天數 | BR-04 |
| 內衣褲 | 6 | 套 | 根據旅遊天數 | BR-04 |
| 保暖外套 | 1 | 件 | 寒冷氣候 | BR-05 |
| 登山鞋 | 1 | 雙 | 登山活動 | BR-05 |
| 登山背包 | 1 | 個 | 登山活動 | BR-05 |
| 身分證件 | 1 | 張 | 國內旅遊 | BR-11 |
| 健保卡 | 1 | 張 | 國內旅遊 | BR-11 |
| 充電器 | 1 | 個 | 共同必備用品 | BR-11 |

旅客可直接依清單準備，省去自行計算衣物及逐項判斷用品的步驟。若標記其中 3 項為已準備，系統應回傳全部 9 項、已準備 3 項、未準備 6 項，完成率為 `3 / 9 × 100%`，並列出那 6 項未準備物品。

推薦後，旅客可新增「個人藥品」1 份、將上衣改為 4 件，或刪除自行判斷不需要的項目。例如在上述 9 項中已有 3 項完成時，新增未準備的個人藥品後為 10 項、完成率 30%；再刪除尚未準備的登山背包後為 9 項、已準備仍為 3 項。這些操作只調整當次清單，不改變推薦規則。

若相同天數、氣候與活動改選 `INTERNATIONAL`，清單中的地區專屬物品改為護照、簽證確認與旅行轉接插頭，仍包含充電器，不因國內規則加入身分證件或健保卡。

## 3. Scope

### In Scope

- 建立旅遊計畫，設定旅遊天數、氣候、活動及旅遊地區類型。
- 根據固定規則自動產生清單並計算建議數量。
- 查詢物品、數量、單位、推薦原因與準備狀態。
- 手動新增物品、修改物品名稱／數量／單位，以及刪除當次清單項目。
- 更新行李項目的準備狀態。
- 計算完成率並列出未準備物品。

### Out of Scope

- 使用者註冊、登入及權限管理。
- 串接國家、簽證、天氣或其他外部 API。
- 大型語言模型推薦、地圖、機票及住宿服務。
- 多人協作與清單共享。
- 自訂或修改推薦規則、可重複使用的清單範本。
- 修改旅遊條件後重新產生清單（BR-09）。
- 行李重量與航空公司限制計算、通知提醒、清單匯出與列印。

設計使用六條 API：新增與刪除各增加一條，修改沿用原有 PATCH。維持 `Trip`、`PackingItem` 兩個 Entity；`Trip` 包含 `region: Enum(DOMESTIC, INTERNATIONAL)`，`PackingItem` 維持既有欄位，不新增 Entity 或欄位。`quantity` 代表目前數量，初始為推薦或手動新增數量；`reason` 保留原始推薦或新增依據。

## 4. Business Rules

### BR-01：旅遊天數

旅遊天數必須為 1～30 天的整數。

### BR-02：氣候類型

每趟旅行只能選擇一種：`WARM`（溫暖）、`COLD`（寒冷）、`RAINY`（雨季）。

### BR-03：活動類型

每趟旅行只能選擇一種：`SIGHTSEEING`（一般觀光）、`BEACH`（海邊）、`HIKING`（登山）。

### BR-04：基本衣物數量

| 物品 | 建議數量 | 單位 |
| --- | --- | --- |
| 上衣 | 旅遊天數 | 件 |
| 褲子 | ceil(旅遊天數 / 2) | 件 |
| 內衣褲 | 旅遊天數 + 1 | 套 |

`ceil` 表示無條件進位至整數。

### BR-05：氣候與活動用品

| 條件 | 額外推薦物品 |
| --- | --- |
| COLD | 保暖外套 1 件 |
| RAINY | 雨具 1 件 |
| BEACH | 泳衣 1 套 |
| HIKING | 登山鞋 1 雙、登山背包 1 個 |
| WARM、SIGHTSEEING | 各自不額外增加專屬物品；仍套用其他符合的規則 |

### BR-06：去重

若同一物品符合多項推薦規則，清單中只保留一筆，建議數量取最大值。

此合併規則適用於自動推薦；手動新增或修改造成同名物品時，依 BR-12 拒絕操作，不自動合併。

### BR-07：初始準備狀態

所有新產生的行李項目（含手動新增）預設為未準備（`is_packed = false`）。

### BR-08：完成率

依行李項目數量計算，非物品件數：`完成率 = 已準備項目數 / 全部項目數 × 100%`。若清單為空，完成率定義為 0%，避免除以零。

項目數、完成率與未準備清單皆依目前清單計算，反映手動新增、修改、刪除及準備狀態更新的結果。

### BR-09：不重新產生清單

本階段不提供修改旅遊條件後重新產生清單的功能。

### BR-10：旅遊地區類型

`region` 為必填欄位，僅接受 `DOMESTIC`（國內旅遊）或 `INTERNATIONAL`（國外旅遊）。

### BR-11：地區與共同必備用品

依旅遊地區類型推薦對應的旅行文件及用品，並加入共同必備用品：

| 條件 | 物品 | 建議數量 | 單位 | 推薦原因 |
| --- | --- | ---: | --- | --- |
| DOMESTIC | 身分證件 | 1 | 張 | 國內旅遊 |
| DOMESTIC | 健保卡 | 1 | 張 | 國內旅遊 |
| INTERNATIONAL | 護照 | 1 | 本 | 國外旅遊 |
| INTERNATIONAL | 簽證確認 | 1 | 項 | 國外旅遊：請自行確認簽證需求 |
| INTERNATIONAL | 旅行轉接插頭 | 1 | 個 | 國外旅遊 |
| DOMESTIC、INTERNATIONAL | 充電器 | 1 | 個 | 共同必備用品 |

「簽證確認」只是提醒使用者自行確認簽證需求，不代表系統已判定是否需要簽證。地區專屬物品僅由對應地區規則加入，所有物品沿用 BR-06 去重及數量取最大值。

上述推薦條件適用於初始自動產生的清單；後續允許使用者自行調整，不強制補回已刪除或覆寫已修改的推薦項目。

### BR-12：手動輸入與同名檢查

新增時必須提供 `name`、`quantity`、`unit`。名稱及單位須為去除前後空白後非空的字串，儲存時去除前後空白；數量須為正整數。修改時，提供的欄位也須符合相同規則。

同一趟旅行不得出現同名物品，以去除前後空白後的名稱完全相同判定，不做同義詞或大小寫轉換。新增或修改名稱若與另一項目重複，回傳 HTTP 400，不合併、不改變原有資料；修改時排除該項目自身。不同旅遊計畫可以有同名物品。

### BR-13：可修改欄位與原因

系統推薦及手動新增的項目皆可修改 `name`、`quantity`、`unit`、`is_packed`。PATCH 至少提供其中一個欄位，僅更新提供的欄位，其餘保持原值；`is_packed` 須為 Boolean。內容修改不自動重設準備狀態，除非同時提供新的 `is_packed`。

`id`、`trip_id`、`reason` 不可由使用者設定或修改。手動新增的 `reason` 固定為「使用者自行新增」；修改既有項目時保留原始原因，代表最初的推薦或新增依據，不重新計算推薦。`quantity` 儲存目前數量，使用者設定可覆寫原建議數量，不另存歷史版本。

空的 PATCH、未知或不可寫欄位、`null` 或不合法型別及值皆回傳 HTTP 400，不部分套用變更。

### BR-14：刪除與所屬計畫

使用者可刪除任何項目，包括護照等系統推薦文件及用品；刪除後不自動補回，不提供復原功能。可刪除全部項目，空清單進度依 BR-08 計算。

新增前須確認旅遊計畫存在；修改或刪除前須確認項目屬於指定 `tripId`。找不到計畫、項目或項目不屬於指定計畫時，回傳 HTTP 404，不影響其他計畫。

## 5. Functional Requirements 與 Acceptance Criteria

### FR-01：建立旅遊計畫

使用者可以輸入旅遊天數、氣候類型、活動類型及旅遊地區類型，建立旅遊計畫。對應 BR-01、BR-02、BR-03、BR-10。

Acceptance Criteria：

- 輸入有效的四項條件時，成功建立計畫並回傳 `tripId`；建立成功回傳 HTTP 201。
- 旅遊天數必須為 1～30 的整數；0、31、非整數等不合法輸入回傳 HTTP 400。
- 氣候與活動各選一種，值須符合 BR-02、BR-03 的 Enum；不合法輸入回傳 HTTP 400。
- `region` 必填，僅接受 `DOMESTIC` 或 `INTERNATIONAL`；缺漏、`null`、非字串或其他值皆回傳 HTTP 400。
- 旅遊計畫回應包含與輸入一致的 `region`。

### FR-02：自動產生行李清單

建立計畫時，系統必須依四項旅遊條件，自動產生包含推薦物品、數量、單位與推薦原因的建議行李清單。對應 BR-04、BR-05、BR-06、BR-07、BR-11。

Acceptance Criteria：

- 依 BR-04 計算基本衣物數量；例如 5 天應產生上衣 5 件、褲子 3 件、內衣褲 6 套。
- 依氣候與活動套用 BR-05 的用品及數量；WARM 與 SIGHTSEEING 不額外增加專屬物品。
- `DOMESTIC` 必須包含身分證件與健保卡。
- `INTERNATIONAL` 必須包含護照、簽證確認與旅行轉接插頭。
- 兩種類型皆包含充電器。
- 國內與國外的專屬物品不得因另一地區的規則而被加入。
- BR-11 的新增物品建議數量皆為 1，單位及推薦原因依該表設定；簽證確認須保留自行確認需求的提醒。
- 每個項目包含名稱、建議數量、單位及推薦原因。
- 同一物品只出現一次；若多項規則推薦同一物品，依 BR-06 保留最大數量，不相加。
- 所有新項目的 `is_packed` 皆為 `false`。
- 旅遊計畫與行李清單須一起建立，不得出現僅建立 Trip、未建立對應 PackingItem 的不完整成功結果。
- 上述物品與建議數量條件用於初始推薦；後續個人調整依 FR-05～FR-07，不重新套用推薦覆蓋調整結果。

### FR-03：查詢及更新行李準備狀態

使用者可以查詢指定旅遊計畫的行李清單，並將物品標記為已準備或未準備。準備狀態起始值依 BR-07，更新驗證與所屬檢查依 BR-13、BR-14；本功能不修改旅遊條件或重新產生清單（BR-09）。

Acceptance Criteria：

- 可依 `tripId` 查詢該計畫的所有行李項目，成功回傳 HTTP 200。
- 可依 `tripId` 與 `itemId` 更新 `is_packed` 為 `true` 或 `false`，成功回傳 HTTP 200。
- 更新後再次查詢可取得最新準備狀態。
- 更新前須確認 `itemId` 屬於指定的 `tripId`。
- `is_packed` 非 Boolean 或其他不合法 PATCH 輸入時，依 BR-13 回傳 HTTP 400，不更新資料。
- 找不到指定旅遊計畫或項目時，回傳 HTTP 404。

### FR-04：查詢行李準備進度

系統根據行李項目的準備狀態計算完成率，並列出未準備物品。對應 BR-08。

Acceptance Criteria：

- 查詢成功回傳 HTTP 200，包含全部、已準備、未準備項目數、完成率與未準備物品清單。
- 完成率依項目數計算，不因同一項目的建議數量不同而加權。
- 例如 10 項中有 7 項已準備，應回傳已準備 7 項、未準備 3 項、完成率 70%，並列出那 3 項物品。
- 若清單為空，項目數皆為 0、完成率為 0%、未準備物品清單為空。
- 找不到指定旅遊計畫時，回傳 HTTP 404。
- 新增未準備項目後，全部與未準備項目數各增加 1；刪除項目後，全部及該狀態項目數各減少 1，完成率依目前清單計算。
- 僅修改名稱、數量或單位時，項目數與完成率不變；未準備清單須反映最新內容。

### FR-05：手動新增行李項目

使用者可在指定旅遊計畫中新增個人需要的物品。對應 BR-07、BR-08、BR-12、BR-13、BR-14。

Acceptance Criteria：

- 對存在的計畫提供合法名稱、數量及單位時，回傳 HTTP 201 與新項目（含 `itemId`），項目屬於指定 `tripId`。
- 新項目 `reason` 為「使用者自行新增」、`is_packed` 為 `false`，可於再次查詢清單及進度時取得。
- 缺漏必填欄位、空白名稱／單位、非正整數數量或同名項目皆回傳 HTTP 400，原清單保持不變。
- 不接受自行指定 `id`、`trip_id`、`reason`、`is_packed` 或其他欄位；回傳 HTTP 400。
- 計畫不存在時回傳 HTTP 404。

### FR-06：修改行李項目內容

使用者可修改系統推薦或手動新增項目的名稱、數量及單位，與 FR-03 的準備狀態更新共用 PATCH。對應 BR-08、BR-12、BR-13、BR-14。

Acceptance Criteria：

- 可單獨修改名稱、數量或單位，也可同時更新準備狀態；成功回傳 HTTP 200 與更新後項目。
- 未提供的欄位保持原值；僅調整內容時，原準備狀態與原因不變。
- 例如將上衣由 5 件調整為 4 件，再次查詢應為 4 件，不重新套用推薦數量。
- 名稱改為同趟旅行另一項目的名稱時，回傳 HTTP 400；保留自身原名不視為重複。
- 空請求、不合法欄位、型別或值回傳 HTTP 400，整筆修改不生效。
- 找不到計畫、項目或所屬計畫不符時回傳 HTTP 404。

### FR-07：刪除行李項目

使用者可刪除當次旅行中不需要的任何項目。對應 BR-08、BR-14。

Acceptance Criteria：

- 可刪除系統推薦或手動新增的項目，成功回傳 HTTP 204，無回應內容。
- 再次查詢清單及進度時不包含已刪除項目，且不自動重新推薦該項目。
- 刪除已準備項目時，已準備項目數亦須減少；刪除最後一項後回傳空清單與 0% 完成率。
- 找不到計畫、項目或所屬計畫不符時回傳 HTTP 404；重複刪除已不存在的項目亦為 HTTP 404。

## 6. 需求追蹤摘要

| 需求 | 主要規則／限制 | 規劃 API |
| --- | --- | --- |
| FR-01 | BR-01、BR-02、BR-03、BR-10 | POST `/trips` |
| FR-02 | BR-04、BR-05、BR-06、BR-07、BR-11 | POST `/trips` |
| FR-03 | BR-07、BR-09、BR-13、BR-14 | GET `/trips/{tripId}/items`；PATCH `/trips/{tripId}/items/{itemId}` |
| FR-04 | BR-08 | GET `/trips/{tripId}/progress` |
| FR-05 | BR-07、BR-08、BR-12、BR-13、BR-14 | POST `/trips/{tripId}/items` |
| FR-06 | BR-08、BR-12、BR-13、BR-14 | PATCH `/trips/{tripId}/items/{itemId}` |
| FR-07 | BR-08、BR-14 | DELETE `/trips/{tripId}/items/{itemId}` |

詳細 API、OpenAPI 與架構文件將於後續階段撰寫；本文件的驗收條件為設計依據，尚未執行系統測試。
