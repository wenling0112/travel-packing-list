# 旅遊行李清單管理系統(Travel Packing List) — AI Collaboration

本文件依實際對話整理「學生原想法／Prompt → AI 建議 → 學生判斷與修正 → 文件結果」，不重現完整對話，也不補造尚未發生的討論或審查。專案維持 Design Only。

## 第一輪：新增旅遊地區條件，修正文件產出順序

### 學生原想法／Prompt

要求在旅遊天數、氣候及活動之外，新增必填的旅遊地區類型：`DOMESTIC`、`INTERNATIONAL`。依地區推薦文件與用品，保留去重規則，不增加 Entity、API 或外部服務。

### AI 的處理與建議

AI 檢查目錄後，發現當時只有初步規劃與作業規範 PDF，尚無 README 或 docs 文件，因此提出更新既有規格並補齊文件，且曾先產生需求文件。

### 學生判斷與修正

學生明確要求：「先幫我修改一下初步規劃.md就好，先確認好初步規格再寫文件」，修正 AI 直接擴大文件產出範圍的做法。之後另要求將題目改為「旅遊行李清單管理系統(Travel Packing List)」。

### 文件結果與取捨

- AI 移除提前產生的需求文件與暫存腳本，先只更新初步規劃。
- 新增 `Trip.region`、BR-10、BR-11，更新 FR-01、FR-02，保留既有編號。
- 國內推薦身分證件與健保卡；國外推薦護照、簽證確認及旅行轉接插頭；兩種類型皆推薦充電器。
- 簽證確認僅為自行確認需求的提醒，不判定簽證需求；沿用 BR-06 去重。
- 本輪仍維持原有四條 API。後續因學生新增個人清單調整需求，才於第三輪調整為六條。

這是一次實際修正 AI 做法的例子：先確認規格，再依學生指定的階段撰寫文件。後來學生明確要求依作業規範產出 README 與需求文件後，AI 才建立這兩份文件。

## 第二輪：檢查題目規模與聚焦小亮點

### 學生原想法／Prompt

「幫我找出題目是否過大，並提出可能的小亮點；先問我問題，不要直接產出全部文件。」

### AI 建議

AI 先詢問主要困擾、主要情境及希望突出的亮點，並初步判斷當時的四條 API、兩個 Entity 與單一準備流程，規模仍合理。

### 學生判斷與選擇

學生回答：

- 自動推薦與準備追蹤兩者都需要，但以自動推薦為主。
- 希望聚焦「第一次出國旅行」。
- 作業重點選擇「依國內／國外提醒對應文件與用品」。

### 建議結果與目前狀態

AI 建議以第一次出國、不確定應準備哪些文件與用品的旅客為主要情境，讓地區推薦成為具體亮點，進度追蹤作為輔助；保留國內選項以呈現推薦差異，無須增加外部 API。

本輪先進行討論，沒有修改文件。現有 README 與需求文件仍以五天國內登山作為完整計算範例，並補充國外情境差異；尚未將「第一次出國」改寫為文件中的主要範例，不將討論方向記為已完成的文件變更。

## 第三輪：加入個人調整，同時控制功能範圍

### 學生原想法／Prompt

「我想要可以讓使用者根據自我需求可以新增、修改、刪除清單內容」，並進一步要求「以規模仍能保持小而完整為主，看能不能增加」。

### AI 建議

將功能限定為「系統先推薦，使用者再調整當次旅行清單」：

- 新增物品須填名稱、數量及單位，原因固定為「使用者自行新增」，預設未準備。
- 可修改名稱、數量、單位及準備狀態；原因不供使用者編輯。
- 可刪除系統推薦或手動新增項目，完成率依目前清單計算。
- 新增與刪除各增加一條 API，修改擴充原有 PATCH，合計六條 API。
- 沿用 Trip、PackingItem，不增加清單範本、自訂推薦規則或重新推薦功能。

### 學生判斷與修正

學生先要求為當時的既有內容準備 commit 訊息，之後明確要求：「接下來幫我修改文件，加入手動新增、修改及刪除清單功能。」

學生因此選擇擴充原本不支援手動調整的範圍，並以保持小而完整為前提，授權 AI 更新文件。對話中沒有逐條確認所有驗證細節，這些細節由 AI 在文件中具體化，不記為學生逐項提出的規則。

### 文件結果與取捨

- README、需求文件及初步規劃納入個人清單調整。
- 保留原編號，新增 FR-05～FR-07、BR-12～BR-14 與對應驗收條件。
- API 從四條調整為六條，兩個 Entity 與既有欄位維持不變。
- AI 補充正整數數量、非空名稱與單位、同名拒絕、項目所屬計畫檢查等規則。
- 所有項目皆可調整，刪除後不自動補回；初始推薦與後續個人修改分開處理。

此取捨讓推薦清單能容納個人用品需求，同時把操作限制在單趟旅行內。六條 API 高於課程建議的 2～4 條，但只增加直接支援清單新增與刪除的兩條操作，未擴充登入、外部服務或其他 Entity。

## 第八輪：確認實作歧義並補足最小規則

### 學生原想法／Prompt

### AI 建議與學生判斷

AI 列出並行修改、同時同名新增、POST 逾時重送、輸入大小、空白字元及多重錯誤順序六項，提出維持六條 API、兩個 Entity 的最小補充規則。學生先要求目前內容的 commit 訊息，待該階段之後才要求：「開始幫我根據檢查後的建議修改文件」。因此先前審查階段未修改規格，本輪依明確指示納入建議，不自行擴充新功能。

| 發現 | 修正文件與內容 | 理由 |
