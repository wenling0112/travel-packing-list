# 旅遊行李清單管理系統(Travel Packing List)

依旅遊天數、氣候類型、活動類型及旅遊地區類型，自動產生包含物品、數量、單位與推薦原因的行李清單，讓使用者依個人需求新增、修改、刪除項目，並追蹤準備進度。

**Design Only（尚未實作）**：本專案為「網際服務軟體工程」課程的個人規劃與設計作業，目前提供設計文件，不包含程式碼、資料庫、可執行 API 或自動化測試。

## 使用者與問題

目標使用者是需要自行規劃與整理行李的一般旅客。每趟旅行的天數、氣候、活動與國內／國外情境不同，旅客常需重新思考攜帶物品與數量，容易遺漏用品或重複規劃。

## 核心亮點與主要情境

核心亮點為「情境式行李推薦與數量計算」：以固定 Business Rules 將四項旅遊條件轉換為可解釋的清單，省去從空白清單逐項規劃的步驟。

系統先推薦，使用者再調整當次旅行的清單，例如新增個人藥品、修改衣物數量或刪除不需要的用品。調整不改變推薦規則，也不重新產生整份清單。

| 條件 | 對推薦的影響 |
| --- | --- |
| 旅遊天數 `days` | 計算上衣、褲子及內衣褲數量 |
| 氣候類型 `climate` | 依 WARM、COLD、RAINY 推薦氣候用品 |
| 活動類型 `activity` | 依 SIGHTSEEING、BEACH、HIKING 推薦活動用品 |
| 旅遊地區類型 `region` | 必選 DOMESTIC 或 INTERNATIONAL，推薦旅行文件及用品，並加入共同必備用品 |

例如：旅客安排 5 天國內登山，選擇 `COLD`、`HIKING`、`DOMESTIC`，系統會建議上衣 5 件、褲子 3 件、內衣褲 6 套、保暖外套 1 件、登山鞋 1 雙、登山背包 1 個、身分證件 1 張、健保卡 1 張及充電器 1 個，共 9 個項目。

若同樣條件改為 `INTERNATIONAL`，地區用品改為護照、簽證確認、旅行轉接插頭及共同的充電器，各 1 個項目。簽證確認僅提醒使用者自行確認簽證需求，不代表系統已判定需要簽證。相同物品依 BR-06 只保留一筆，數量取最大值。

## 核心使用流程

1. 使用者建立旅遊計畫。
2. 輸入旅遊天數，選擇氣候、活動及旅遊地區類型。
3. 系統驗證條件，依固定規則產生行李清單。
4. 使用者查看清單，依個人需求新增物品、修改名稱／數量／單位或刪除項目。
5. 使用者將已準備的物品標記完成。
6. 系統顯示完成率與尚未準備的物品。

## Client–Server／HTTP 情境

設計上由 Client 透過 HTTP 呼叫 Server 的 RESTful API；Server 驗證輸入、套用推薦規則、處理清單調整並回傳結果。規劃以下六條 API，尚未提供可連線的服務：

| Method | Path | 用途 | 需求 |
| --- | --- | --- | --- |
| POST | `/trips` | 建立旅遊計畫並產生行李清單 | FR-01、FR-02 |
| GET | `/trips/{tripId}/items` | 查詢行李清單 | FR-03 |
| POST | `/trips/{tripId}/items` | 手動新增物品 | FR-05 |
| PATCH | `/trips/{tripId}/items/{itemId}` | 修改物品內容或準備狀態 | FR-03、FR-06 |
| DELETE | `/trips/{tripId}/items/{itemId}` | 刪除物品 | FR-07 |
| GET | `/trips/{tripId}/progress` | 查詢準備進度 | FR-04 |

資料模型維持 `Trip` 與 `PackingItem` 兩個 Entity；旅遊地區類型存於 `Trip.region`。

## 系統範圍

In Scope：建立計畫、依四項條件自動推薦與計算數量、查詢清單及原因、手動新增／修改／刪除當次清單項目、更新準備狀態、查詢完成率與未準備項目。

手動新增須填名稱、正整數數量與單位，原因固定為「使用者自行新增」，預設未準備。修改可調整名稱、數量、單位及準備狀態，原因由系統保留、不供編輯。所有項目（含系統推薦文件及用品）皆可修改或刪除；同趟旅行不接受同名物品。完成率依調整後的清單計算，全部刪除時為 0%。詳細規則見需求文件 BR-12～BR-14。

Out of Scope：登入與權限、國家／簽證／天氣或其他外部 API、大型語言模型推薦、地圖／機票／住宿、多人共享、自訂推薦規則、可重複使用的清單範本、行李重量及航空限制、通知、匯出與列印。本階段也不提供修改旅遊條件後重新產生清單的功能。
